# Testing

CI gates two numbers besides the tests themselves: how many tests there are, and how many mutants of the code they catch. Each gate's floor is a ratchet, the value when it was last raised, kept in its script; the README states each floor and target, and `crates/tui/tests/thesis.rs` holds the README, the scripts and the workflows to each other.

## Test count

`scripts/check-test-count.sh` counts the names `cargo test --workspace -- --list` lists (one line ending in `: test` per test, from every test binary and the doc tests) and takes out the ones `cargo test --workspace -- --list --ignored` lists, since no CI job runs an ignored test. Linux and macOS each compile a few tests the other does not, so the script keeps a floor for each and picks it by `uname -s`. CI's test job runs it on both runners after building the suite, and it fails under the runner's floor. On any other platform it reports the count and passes. A change that adds tests raises each floor to the count the script reports on that platform for it: a local run gives that machine's count, and the Check test count step in each runner's test job gives that runner's, naming the floor it can raise. A change that removes tests on purpose lowers the floors and says why.

## Mutation testing

The Mutants workflow (`.github/workflows/mutants.yml`) runs cargo-mutants 27.1.0 with `.cargo/mutants.toml`: each mutant makes one small change to the code, such as a function returning a fixed value or one operator swapped for another, and every test target of the workspace runs against it. Every job builds with the one compiler the workflow pins. A pull request's run tests the mutants in the lines it changes: every mutant whose span holds a changed line, so changing one line of a function also tests the mutants that replace that function's whole body, and a miss among them that predates the change still fails it until a test catches it or `.cargo/mutants-allowed.txt` gives its reason. A run on a push to main, the weekly run, and a run by hand (Actions, Mutants, Run workflow, on any branch) test every mutant in the workspace. Such a run takes hours, so a push to main made while one is going waits, and only the newest push waiting is tested.

Each mutant is caught (a test failed), missed (every test passed), timed out (the tests ran past the larger of 150 seconds and 5 times the time the unmutated tests took), unviable (it does not build), or not built (it is under a `#[cfg(...)]` that is false for the runner's target, such as macOS-only code on Linux, so it changed nothing the tests ran). `.cargo/mutants-allowed.txt` lists mutants with the reason each may survive. A listed mutant that timed out counts as caught, since its reason says why the hang is how it fails; an unlisted timeout counts as missed; a listed miss still counts as missed. The score is caught / (caught + missed); unviable and unbuilt mutants are left out.

### The floor

A full run fails when the score is under the floor in `scripts/check-mutants.sh`: the score of the full run that last raised it, less a margin of 0.20 points. Two runs of the same code do not decide every mutant alike. One pair of runs of one tree has been compared so far: the full run that set the floor, and a run cancelled partway that tested 1,550 of the same mutants. cargo-mutants tests a shard's mutants in the order it finds them, file by file, so those 1,550 are all in open-max-core (20 of its files, some only in part), and none of crates/tui's 3,073 mutants has been tested twice. The two runs differed on 2 of the 1,550 (0.13%): a test whose result under those two mutants turns on how two random session ids sort caught them in one run and missed them in the other. If the whole workspace varies at that rate, about 9 of the 6,975 mutants a full run scores come out differently from one run to the next, either way. The margin is 14 of them, so a run of unchanged code fails only when more than 14 turn from caught to missed; at the highest rate that pair allows with 95% confidence (6.3 in 1,550), that is about 3 runs in 1,000. The first full run on main, set beside the run that set the floor on the files neither changed, is the first pair over the whole workspace, and the margin is derived again from it.

A change that makes the tests catch more raises the floor in the same commit, to the score a full run of that commit reports less the margin; the run's report gives that value (run the workflow by hand on the branch). A change that removes code and its tests on purpose lowers it and says why. A new compiler can move the counts too, so bumping the one the workflow pins is a change of its own, with a full run.

### Reading a run

- **Plan** prints how many mutants the run tests and over how many shards.
- **Shard (k)** first runs every test of the workspace on the unmutated tree, then tests every n-th mutant from the k-th (counting from 0), n being the number of shards Plan printed. Its log has one line per mutant, with its outcome and its build and test time. Its artifact `mutants-shard-k` is cargo-mutants' output directory: `outcomes.json`, the outcome lists (`caught.txt`, `missed.txt`, `timeout.txt`, `unviable.txt`), and for each mutant a file in `diff/` (the change it made) and one in `log/` (the build and test output it got).
- **Mutants in the change** (a pull request) or **Mutation score** (every other run) merges the shards, and fails unless they hold every mutant Plan listed. Its log and the run's summary page give the count of each outcome, the score with its floor and target (or, on a pull request, each mutant that was missed or timed out and is not listed), the missed mutants per file, then each missed mutant by name. On a pull request each one it fails on is also marked on its line in the change. Its artifact `mutants-missed` lists the missed mutants, one per line.
- A shard that fails (a test failed on the unmutated tree, or GitHub lost its runner) fails the run, which then has no score. Re-run the failed jobs of that run: a shard run again replaces the outcomes its failed attempt kept, if any, and the last job then merges the new shard's outcomes with the others'. A test that fails on the unmutated tree again is named in the shard's log, and needs fixing before any mutant can be judged.

A missed mutant is a change to the code that no test noticed. Write a test that fails with that change applied (its `diff/` file shows the change, and `patch FILE DIFF` applies it), or list it in `.cargo/mutants-allowed.txt` with the reason it may survive. A mutant no test can observe is excluded in `.cargo/mutants.toml`, with the reason.
