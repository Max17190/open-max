# Testing

CI gates the test count on every pull request and push to main. Scheduled and manual mutation runs separately gate how many mutants the tests catch. Each gate's floor is a ratchet, the value when it was last raised, kept in its script; the README states each floor and target, and `crates/tui/tests/thesis.rs` holds the README, the scripts and the workflows to each other.

## Suite timing

The functional tests run under cargo-nextest, each test in a process of its own, as many at once as the runner has cores, under the ci profile of `.config/nextest.toml`, which retries no test. CI's Suite time job builds the suite on ubuntu-latest and runs `scripts/check-suite-time.sh` there, every test binary at once with its own thread pool, against a 15-second budget, and fails the pull request over it. macos-latest is not gated: its three shared cores ran the suite in 12.5 to 33.7 seconds over 32 runs, over its 20-second budget in 19, so the Reports workflow runs the check there every night, five times after one build, and reports each run and the median; it fails only when the runs did not finish. The suite timing is also the one gating step that runs a binary's tests as threads of one process, as `cargo test` does, where a binary that fails beside the others is run once more alone, its tests still threads of one process, and fails the check only if it fails again, and where the two tests that time their own work in a debug build too run alone after the others, on the same clock; the thesis job runs one test at a time.

## Test count

`scripts/check-test-count.sh` counts the names `cargo test --workspace -- --list` lists (one line ending in `: test` per test, from every test binary and the doc tests) and takes out the ones `cargo test --workspace -- --list --ignored` lists, since no CI job runs an ignored test. Linux and macOS each compile a few tests the other does not, so the script keeps a floor for each and picks it by `uname -s`. CI's test job runs it on both runners after building the suite, and it fails under the runner's floor. On any other platform it reports the count and passes. A change that adds tests raises each floor to the count the script reports on that platform for it: a local run gives that machine's count, and the Check test count step in each runner's test job gives that runner's, naming the floor it can raise. A change that removes tests on purpose lowers the floors and says why.

## Mutation testing

The Mutants workflow (`.github/workflows/mutants.yml`) runs cargo-mutants 27.1.0 with `.cargo/mutants.toml`: each mutant makes one small change to the code, such as a function returning a fixed value or one operator swapped for another, and every test target of the workspace runs against it. Every job builds with the one compiler the workflow pins. The weekly run and a run by hand (Actions, Mutants, Run workflow, on any branch) test every mutant in the workspace, with at most four shards running concurrently. These sweeps take hours and do not run automatically on pull requests or pushes to main. Runs on the same branch queue; a newer pending run replaces an older pending run.

For a targeted local check, first run `cargo test --workspace --locked` and stop if it fails: cargo-mutants checks only the selected packages before mutation, but tests every package against each mutant. Then save the change against its base with `git diff origin/main...HEAD > /tmp/openmax-change.diff`, run `cargo mutants --in-diff /tmp/openmax-change.diff`, record the target with `rustc --print cfg > mutants.out/cfg.txt`, and judge the resulting directory with `scripts/check-mutants.sh --diff mutants.out`. This optional check fails for a missed, timed-out or signalled mutant unless `.cargo/mutants-allowed.txt` documents why it may survive. A function replacement mutant can span a changed line even when the function's other lines are unchanged.

Each mutant is caught (a test failed), missed (every test passed), timed out (the tests ran past the larger of 150 seconds and 5 times the time the unmutated tests took), signalled (a signal ended cargo while it built the mutant or ran its tests, as when the kernel kills it at the shard's memory cap; cargo-mutants records such a mutant as a Failure), unviable (it does not build), or not built (it is under a `#[cfg(...)]` that is false for the runner's target, such as macOS-only code on Linux, so it changed nothing the tests ran). `.cargo/mutants-allowed.txt` lists mutants with the reason each may survive. A listed mutant that timed out or was signalled counts as caught, since its reason says why the hang or the signal is how it fails; an unlisted one counts as missed, since no test failed; a listed miss still counts as missed. The score is caught / (caught + missed); unviable and unbuilt mutants are left out. The judge refuses a run with any other outcome: a mutant that was only checked, never built or tested (a run with `--check`), a Failure no signal ended, or a summary cargo-mutants 27.1.0 does not write.

### The floor

A full run fails when the score is under the floor in `scripts/check-mutants.sh`: the score of the full run that last raised it, on the basis below, less a margin of 0.26 points. The floor was set by the full run on 2d139e8 of 2026-11-02 (Actions run 41444364783), which tested 8,478 mutants and caught 6,783 of the 8,024 it scored: 84.53%. The floor's basis leaves out 191 of those catches, which cannot be told from chance: 6,592 caught of the 8,024, 82.15%, so the floor is 81.89%, not the 84.27% the run's report offered.

For those 191 mutants the only test to fail was `first_frame::provider_setup_hides_keys_and_returns_input_to_the_same_tui`, in `crates/tui/tests/frame_io.rs`, at its deadline for the terminal's keyboard probe. It failed that way for one of them that `.cargo/mutants-allowed.txt` lists as equivalent, which behaves exactly as the code it changes, and for a mutant in code Linux does not compile, which the score leaves out and which changed nothing the test ran. So a catch that failure alone made cannot be told from chance, and the basis leaves all 191 out: a change that stops the test failing by chance takes away nothing the floor rests on, and any of them that a test does catch counts when a later run raises the floor.

Two runs of the same code do not decide every mutant alike: a test that fails by chance, such as one with a timing bound that a loaded runner misses, catches whichever mutant it ran under. Two full runs on main tested the same code: Actions run 39644754820 on 2026-10-21 and run 40304868989 on 2026-10-26, of the trees of fa18395a (#414) and c47ddc13 (#420) on main, which differ only in README.md. Of the same 7,748 mutants they scored 7,332 and 7,331, and decided 44 differently (0.60%); of the 19 that the second run caught and the first missed, 16 were caught only by a test's timing bound. Each mutant that differs moves the caught count by one, either way, so the caught counts of two runs of unchanged code differ by a net whose standard deviation is the square root of how many differ. At the highest rate that pair allows with 95% confidence (56.6 in 7,331), 62 of the 8,024 would differ, a standard deviation of 7.9. The margin is 21 of them, so a run of unchanged code, those 191 aside, fails only when more than 21 turn from caught to missed: about 3 runs in 1,000 at that pair's rate. The pair predates the keyboard-probe test, so the margin is derived again from the next full run on main, set beside 2d139e8's on the files that did not change between them.

A change that makes the tests catch more raises the floor in the same commit, to the score a full run of that commit reports less the margin; the run's report gives that value (run the workflow by hand on the branch). A change that removes code and its tests on purpose lowers it and says why. A new compiler can move the counts too, so bumping the one the workflow pins is a change of its own, with a full run.

### Reading a run

- **Plan** prints how many mutants the run tests and over how many shards.
- **Shard (k)** first runs every test of the workspace on the unmutated tree, then tests every n-th mutant from the k-th (counting from 0), n being the number of shards Plan printed. Its log has one line per mutant, with its outcome and its build and test time. Its artifact `mutants-shard-k` is cargo-mutants' output directory: `outcomes.json`, the outcome lists (`caught.txt`, `missed.txt`, `timeout.txt`, `unviable.txt`; a signalled mutant is only in `outcomes.json`), and for each mutant a file in `diff/` (the change it made) and one in `log/` (the build and test output it got).
- **Mutation score** merges the shards and fails unless they hold every mutant Plan listed. Its log and the run's summary page give the count of each outcome; the score with its floor and target and, when the score is at or above its floor, how many of the missed would meet the target; each file's score, worst first, with how many of its missed would bring it to 90%; the signalled mutants with the phase and signal; the mutants not built for the target; then each missed mutant by name. Its artifact `mutants-missed` lists the missed mutants, one per line.
- A shard that fails (a test failed on the unmutated tree, or GitHub lost its runner) fails the run, which then has no score. Re-run the failed jobs of that run: a shard run again replaces the outcomes its failed attempt kept, if any, and the last job then merges the new shard's outcomes with the others'. A test that fails on the unmutated tree again is named in the shard's log, and needs fixing before any mutant can be judged.

A missed mutant is a change to the code that no test noticed. Write a test that fails with that change applied (its `diff/` file shows the change, and `patch FILE DIFF` applies it), or list it in `.cargo/mutants-allowed.txt` with the reason it may survive. A mutant no test can observe is excluded in `.cargo/mutants.toml`, with the reason.
