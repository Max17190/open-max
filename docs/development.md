# Development

Found a bug or want a change? Open an issue or send a PR.

```sh
cargo check
cargo test
scripts/check-suite-time.sh
scripts/count-core-lines.sh
scripts/check-test-count.sh
scripts/core-share.sh
scripts/gate-time.sh --repo Max17190/open-max
cargo build --release -p openmax
```

`cargo test` runs the test binaries one after another. `scripts/check-suite-time.sh`, run once they are built, runs them all at once and fails when the suite takes longer than 5 seconds, or when a test fails (a test binary that fails beside the others is run again alone and fails the check only if it fails again). The two tests that time their own work and hold it to a bound in a debug build too, `harness_time_per_tool_round` and `a_hundred_extensions_load_in_under_10_ms`, would time the runner beside the others, so they run alone after them, on the same clock, and fail the check when they fail there. A test binary still running at three times the budget is stopped, with every process still under it, and fails the check, which names the tests it had not finished. CI's test job runs every test under cargo-nextest, each in a process of its own and none retried (`.config/nextest.toml`). No pull request is gated on the suite's time: a shared runner's own speed decided it, as ubuntu-latest took 15.04 to 18.80 seconds against its three-times budget (15 seconds) in 11 runs over one week with every test passing, and macos-latest's three shared cores ran the suite in 12.5 to 33.7 seconds over 32 runs, over its four-times budget (20 seconds) in 19. So the Reports workflow runs the script on both runners every night, five times after one build, and reports each run and the median. One run says little about the next, so `scripts/check-suite-time.sh --runs 10` runs the suite ten times after one build, prints each run's time, slowest binary and 1-minute load average, then the median and the slowest run, and fails when any run fails. The script, and the test in `crates/tui/tests/thesis.rs` that drives it as part of `cargo test`, need bash and perl with its core modules JSON::PP and Time::HiRes (on Debian and Ubuntu, the `perl` package: `perl-base` alone has neither).

Test builds optimize the workspace's two crates, `open-max-core` and `openmax`, at level 2 (`[profile.test.package]` in `Cargo.toml`, which gives what that saves the suite and what it costs a build); `cargo build` and `cargo run` build them unoptimized. CI's test job and the Mutants workflow build the tests with them unoptimized too, the build every debug bound was set on, and the Reports workflow's suite timing times the optimized one. To build your own tests unoptimized, add `[profile.test.package.open-max-core]` and `[profile.test.package.openmax]`, each holding `opt-level = 0`, to `~/.cargo/config.toml`.

The thesis tests (in every `crates/*/tests/thesis*.rs` and the binary's `thesis_frames` module) are each named for what they assert, and each whose name states a bound, such as `frozen_prefix_is_under_700_tokens`, prints a `MEASURE` line keyed by its name that gives that bound: `every_thesis_gate_named_for_a_bound_prints_its_measurement_and_bound` holds that, and that CI's thesis job gates each of them. One that times the harness asserts its bound only in a release build, and a 20x sanity bound in debug; a byte or count one asserts the same in every build. CI's thesis job builds them in release, the profile the published binary ships with, and runs them on Linux and macOS in a step that fails the pull request, except the ones a runner reports instead, listed in its matrix entry in `.github/workflows/ci.yml`. The Reports workflow (`.github/workflows/reports.yml`) runs those every night instead, in release on the same runners, and copies each `MEASURE` line to its job's summary; it runs on no pull request, and fails only when a reported test printed no `MEASURE` line. A runner that reports every test of the `thesis_frames` module, macOS today, builds no release copy of the binary's unit-test harness that holds them, a whole-program LTO unit its gates would run no test from (`frames` in its matrix entry). No step of the pull request's gate is skipped in a run that decides it, or may fail without failing it, through `continue-on-error`, an `if:` other than `${{ !cancelled() }}` or a failure its script swallows (`|| true`, or `set +e` or `set +o pipefail`), and every step runs under bash with `pipefail`, so no pipe loses one (`pull_request_workflows_skip_no_step_and_let_none_fail`). Today the reported tests are `harness_time_per_tool_round` (target 250 us) on both runners and `transcript_frame_p99_at_100k_lines` (target 0.5 ms) and `transcript_frame_p99_at_1m_lines` (target 0.25 ms) on macOS, targets those runners do not meet with room. On Linux, where ubuntu-latest measured the 1,000,000-line frame's p99 at 0.131 to 0.305 ms over its first three runs, a release build holds it to a ratchet of 0.41 ms until it meets its target. The first frame's 1 ms target is not asserted in CI: timed from the spawn, a frame includes the runner's own process start, which is not the harness's work. CI holds instead the ratio of the first frame's median to the median start of a baseline binary (`crates/tui/examples/startup_baseline.rs`, which writes the end of a frame and exits), timed the same way on the same runner, under a ratchet of 2.0 on macOS and 2.9 on Linux, and prints both times and their difference, the harness's own work, without asserting the work. A release build on the reference machine's class, an Apple M5, which CI's runners are not, asserts the work too: it times 61 launches instead of 21 and holds the work under a ratchet of 450 us where the baseline binary's median is no slower than 1.18 ms. That reach is the 90th percentile of the baseline medians in the first measurement of each of the reference machine's runs (1.174 ms), rounded up to 10 us, and the ratchet is the median work of its measurements within the reach (408 us), plus a tenth, rounded up to 10 us. A measurement over the ratchet, or past its reach, is taken again, up to 3 measurements in all, and the work fails only when each one the ratchet reaches is over, since a burst of other work on the machine slows a measurement or two while a change that adds work slows every one; where each baseline median is slower, as on a machine busy with other work, the work is reported and not asserted. The work's target of 100 us is not met, and the test prints it with the measurement in a `MEASURE` line. Most of the work left is the dynamic loader's, before `main`: it binds each of the binary's imports at launch by searching libSystem's re-exported libraries in order, and the 115 among them that the baseline binary does not import cost a copy of it 276 to 297 us and 6.46M instructions there by themselves, nearly three times the target (the test's doc comment gives the attribution). `the_binary_names_only_libsystem_caps_its_imports_and_chains_its_fixups` holds the loader's share down: the binary names libSystem alone and binds at most 183 libSystem imports in a release build on Apple silicon, where its fixups are chained, in the pointer format the linker writes for macOS 11 (`crates/tui/build.rs`).

The frozen prefix meets its 700-token target: `frozen_prefix_is_under_700_tokens` (`crates/core/tests/thesis.rs`) prices what every request resends first, messages[0] without the project path plus the `tools` array and the note that follows, against a 3,036-byte cap, which is 700 tokens less a 10-token allowance for one path at 4.4 bytes per token, and measures 3,019 bytes, about 685 tokens, today. Peak memory does not meet its target yet: `headless_turn_peak_rss_stays_under_its_ratchet` reports a two-round turn's peak RSS, from `wait4`, against a 4,000,000-byte target, which a release build misses at 6,544 KiB by median today. What that test enforces is a ratchet, on macOS Apple silicon in a release build only, over a second series of the same runs started with `MallocMaxMagazines=1`: 4,224 KiB beyond the binary's own floor, 32 KiB of it raised for the update notice and `/update`, 96 KiB for redacting credentials in tool results, and 80 KiB for setting the request budget from the turn's pace. Anywhere else it asserts a sanity bound of twenty times the target, and on Linux every figure starts from the test process's own high-water mark, so it bounds the turn's from above.

A prompt cache could serve at least 75% of what a session sends: `a_session_prompt_is_75_percent_cacheable` in `crates/core/tests/thesis.rs`, with its Responses and native Messages twins, drives one 26-request session against a scripted endpoint (tool rounds whose replies carry reasoning, a tool write that stores the note, a steer, a compaction with its notes request, and a resume from the session's files) and takes, for each request, the longest prefix of its prompt (its tools and system prompt, in the order the provider renders them, then the conversation) that it shares byte for byte with an earlier request: the most any provider's cache could serve it, so what the harness rewrites is lost everywhere. It fails when a request rewrites a byte the request before it sent, except the two the compaction makes, which it names; when the compaction's notes request does not carry the turn's tools and system prompt, or sends a byte ahead of its ask that no earlier request sent; when a request after the first shares its tools and system prompt whole with no earlier one; and when the share, in tokens by the harness's estimator, falls under the 75% target or under its ratchet. The ratchets are 87.9% (Chat Completions), 87.9% (Responses) and 88.1% (native Messages), each the share when it was set, 88.49%, 88.49% and 88.60%, less half a point, rounded down to a tenth.

The Responses and native Messages twins also print what a provider bills as cached, where its cache ends entries at message or block boundaries rather than at any byte: on Responses by OpenAI's implicit caching on GPT-5.6 and later, whose entry ends at a request's latest user message or tool output, and on native Messages by Anthropic's, whose entries end at the blocks a request marks with `cache_control`. The harness stores the note in the history where it changes, so the entry each request writes holds it and the next request reads it back. The native Messages client marks the end of the system prompt and each request's newest block. Each twin fails when a request, the compaction's two aside, reads back no entry the request before it wrote, and when that billed share falls under the 75% target or its ratchet, 87.1% billed (Responses) and 87.2% billed (native Messages), each the share when it was set, 87.66% and 87.76%, less half a point, rounded down to a tenth; with the note at the end of the last message and no block marked, they were 0.00%. A Chat Completions server caches a byte prefix, so the bound above is what it can bill.

The note is stored once, where it changes: `a_note_is_stored_once_where_it_changes` in `crates/core/tests/thesis.rs` drives a nine-request session that writes a tool and then a skill, over each protocol, and fails when a request does not repeat every byte the request before it sent, when its last request does not carry each of the two notes once, when a request does not read back the entry the request before it wrote, or when a native Messages request does not replay the thinking of every reply before it, which the client sends back only while the history that reply answered is unchanged. Sent after the history of each request and dropped by the next, the note left native Messages replaying the thinking of 8 of the 36 replies it could, and 74.62% (Responses) and 74.36% (native Messages) billed as cached; stored, 36 of 36, 76.84% and 76.76%.

Parsing and registering 100 extensions takes under 10 ms: `a_hundred_extensions_load_in_under_10_ms` in `crates/core/tests/thesis.rs` builds 100 extensions of every kind, three fifths in the project and the rest global (40 tool manifests with parameter schemas, half of them with examples, 30 skills, 10 prompt templates, 10 approved hooks and 10 permission rules), checks that one load registers every one of them, and times one pass over them in ask mode: the registry's build, the prompt's skills index, the hook discovery with its approval check and the permission rules, which a session runs when it starts, and the template discovery the terminal UI runs when `/` opens its completion. A session's first turn does more with its extensions than this pass, and the test does not time that work: the turn captures the tools and skills a second time for its refreeze check, fingerprints the hooks, and outside auto checks each external tool's content approval, reading the ledger and binding the tool's code every time. A release build asserts the 10 ms target on the median of 101 loads, about 3 ms on the reference machine (Apple M5), and on a machine of the reference machine's class holds a load to at most 3.2 times the time to read their files, 10% over the ratio of 2.88 measured on efficiency cores alone, rounded up to a tenth. At full speed the ratio measured 2.67 to 2.74, with the load nearly four times as fast as on those cores, and other work on the same cores moved it to 3.20. Elsewhere, CI's runners included, a release build prints the ratio, whose scale is the machine's own.

What a provider actually served is recorded per session: `scripts/cache-report.sh <sessions dir>` (bash and perl) reads every `<id>.usage.jsonl` there, one line per model request whose reply reported its token usage (any other request counts nowhere), and prints a row per session, then the share of prompt tokens served from cache over the sessions with more than 100,000 prompt tokens (target 75%), the share of sessions that cached no prompt token (target 5%), and the p50 and p90 of the gaps between consecutive requests of a session, a gap over 600 s left out as idle (target p90 90 s). A request that reported no cached tokens counts as uncached, and its row says how many did. `cache_report_measures_recorded_sessions` in `crates/tui/tests/thesis.rs` holds the script's method to synthetic sessions in `crates/tui/tests/fixtures/sessions` on every CI run.

`scripts/count-core-lines.sh` (bash and perl) prints two line counts for each crate and in total: core-excluding-tests, the lines of `crates/*/src` less its test-only code (`#[test]` functions, `#[<path>::test]` functions such as `#[tokio::test]` ones, items under a `cfg` that needs `test`, and the module files those items load, found by matching brackets outside strings, chars and comments, by the method in the script's header; the input of `stringify!` and the rules of a `macro_rules!` are text the build keeps, so no attribute in them is read), and total-including-tests, every line of every `.rs` file under `crates/` (build output in a crate's `target/` directory aside), so a test's lines count toward total-including-tests wherever they sit and toward core-excluding-tests nowhere. With `--files` it also prints a row for each `.rs` file a crate's counts read, the file's two counts and then its path, so a crate's file rows add up to its row. The script stops with an error naming the file and line of a test-only item whose end it cannot find, rather than guess. `scripts/check-test-count.sh` counts the tests `cargo test --workspace -- --list` lists, less the ignored ones, and fails when there are fewer than 1,933 on Linux, or 1,920 on macOS: each compiles a few tests the other does not, so each has a floor of its own. CI runs it in the test job on both; on any other platform it reports the count and passes. The target is 2,000 tests.

The Mutants workflow runs cargo-mutants (configured in `.cargo/mutants.toml`) weekly and on demand, with at most four shards running concurrently. It tests every mutant in the workspace on Linux, 8,478 in the run that set the floor, and `scripts/check-mutants.sh` fails the run when the mutation score, caught / (caught + missed), is under 81.89%. That run scored 84.53%, or 82.15% without the 191 catches a test made only by failing at its keyboard-probe deadline, which cannot be told from chance; the floor is the score without them, 82.15%, less a margin of 0.26 points for variation between runs. Mutants in code Linux does not compile, such as macOS-only code, are excluded. These multi-hour sweeps do not run automatically on pull requests or pushes to main; regular tests, lint, thesis gates and release checks still do. The target is 95%, and 90% in each file; the run's report gives each file's score. [Testing](testing.md) explains the outcomes, floor and targeted local checks.

`scripts/core-share.sh` (bash and git) measures where capability lands: the share of the latest 50 first-parent commits of main whose diff against their first parent changes a file under `crates/core/`, so a merge's whole change counts as one commit. With `--csv FILE` it writes one row for each first-parent commit, newest first: its sha, committer date and subject, whether it touches the core, the lines it adds and removes there and elsewhere, and the share over it and the 49 commits before it. CI's core-share job runs it with the whole history on every push to main and every pull request, adds the share to the job's summary and keeps the CSV as the run's `core-share` artifact; on a pull request the newest row is the pull request as a squash merge would land it. The target is at most 20%. Until the share meets it, the job reports the share and fails only when the script cannot measure it.

`scripts/gate-time.sh` (bash, gh and perl) measures the pull-request gate: the CI workflow's jobs, which all start at once (the tests under cargo-nextest with the test count, the examples' scripts, Clippy, the thesis gates, the core share and dist's plan of the release), where a push to a pull request cancels the run still testing its previous head. For each of the latest 20 pull-request runs of the CI workflow that passed at their first attempt, it reads from GitHub the wall clock from the start of its first job to the end of its last, then prints the p50, p90 and p99 of those times by the nearest rank, and how many runs as recent failed at their first attempt or were cancelled. The Gate time workflow runs it on every push to main and every night and adds the report to the job's summary. The target is a p50 under 90 seconds and a p99 under 120 seconds over 20 consecutive runs: the script reports it met only when no run as recent as the oldest of the 20 failed at its first attempt. Until the gate meets it, the job reports the times and fails only when the script cannot measure them. The Release build workflow builds and size-gates every release target on every push to main, every night and every merge group, and on no pull request: the slowest of those builds, on a macOS Intel runner, takes longer than the whole gate. A release tag publishes nothing unless dist builds every target, but it reads no size budget, so a binary over its budget fails main's run of the merge that grew it and no later check: cut a release from a commit whose Release build passed. CI's Release plan job runs `dist plan`, the plan a release tag starts with, on every pull request, so a release config dist cannot plan fails the pull request that makes it. A pull request that changes Cargo.toml or Cargo.lock can run the release builds on its branch with `gh workflow run release-build.yml --ref <branch>` before it merges.
